Blockchain Infrastructure Specification

The Excalibur Global platform is built on a layered blockchain infrastructure deployed on BNB Smart Chain (BSC). The architecture separates on-chain identity and event anchoring from off-chain document storage, using Chainlink oracles to bridge real-world agricultural data to the ledger. Every layer is publicly readable without authentication, enabling trustless consumer verification and regulatory auditability.

Design Invariants Non-Negotiable

Immutability: once written, no record can be altered or deleted. Public readability: all chain state is readable via free BSC RPC with no API key. Off-chain privacy: no personal farmer data appears on the public ledger - only cryptographic commitments. No central gatekeeper: consumers, auditors, and regulators can independently verify every record without involving Excalibur Global servers.

Data Storage System - Decentralized Architecture

On-chain storage is limited to cryptographic commitments (hashes and CIDs). All documents, images, and structured metadata are stored on IPFS and referenced immutably from the blockchain. This design keeps BSC transaction costs minimal while ensuring data permanence.

IPFS Document Schema

Each Farm ID NFT and Harvest Batch NFT stores a single IPFS CID in its token metadata. That CID resolves to a structured JSON document pinned to IPFS:

  "registrationDate": "2026-03-01T00:00:00Z",
  "country": "CM", "region": "Littoral",
  "geoJsonCID": "Qm...",         // boundary polygon
  "kycDocCID":  "Qm...",         // hashed KYC proof
  "cooperativeId": "COOP-002",
  "satelliteVerifyCID": "Qm..."  // NDVI snapshot
}

// Harvest Batch Document (IPFS)
{

  "cropType": "SOY", "variety": "Williams 82",
  "harvestDate": "2026-03-10",

Pinning Strategy

Primary: Pinata cloud pinning service - all CIDs are pinned on document creation.

Redundancy: Excalibur Global runs a local IPFS node with all CIDs re-pinned. Failure of either node leaves the other serving data.

Public access: All IPFS content is readable by anyone via public IPFS gateways (ipfs.io/ipfs/[CID], cloudflare-ipfs.com/ipfs/[CID]). No API key, no authentication.

On-chain anchor: CIDs are stored in NFT token metadata URI and cannot be changed post-mint. Any document alteration produces a different CID that would not match the on-chain record.

MRV Platform Storage

Report generation: User-initiated MRV assessments produce structured JSON reports. These are optionally exported as PDF (jsPDF) or CSV (Google Sheets integration). Enterprise users can auto-save reports to their Google Drive via OAuth2.

No server-side data: All MRV calculations are performed client-side in browser JavaScript. No user data is transmitted to Excalibur Global servers during report generation. Only voluntary submission for verification sends data off-device.

Satellite Data Storage

NDVI snapshots and land-cover classification images retrieved via Chainlink oracle from Sentinel-2 and Landsat-9 are stored as IPFS CIDs. Images are not stored on-chain - only the CID and a SHA-256 hash of the raw NDVI value are written to the XGTFarmRegistry contract. The full raster data is pinned to IPFS and linked from the farm NFT metadata.

Agricultural Traceability Protocol - Technical Specification

The Excalibur Global agricultural traceability system is a five-contract protocol on BNB Smart Chain that transforms every farm, harvest, and supply chain handoff into a permanent, publicly verifiable on-chain record. The system is designed to meet EU Deforestation Regulation (EUDR) due diligence requirements and US USDA import traceability standards while remaining operable by farmers in low-connectivity regions of Africa and South America.

Protocol Guarantees Enforced On-Chain

Every farm identity is a permanent NFT. Every harvest is a tokenized batch with an immutable sustainability score. Every custody transfer is a non-repudiable signed event. Every anomaly flag is permanent and visible to consumers. XGT rewards flow automatically from verified data - no manual Excalibur Global approval at any step. Any consumer with a smartphone can independently verify the full provenance of any product without a wallet, an account, or any crypto knowledge.

1. Farm Identity Protocol

Farm registration is the entry point to the traceability network. It produces a Farm Identity Token (FIT) - an ERC-721 NFT whose token ID is the canonical identifier for every downstream harvest batch and supply chain event from that farm. Registration is a one-time, permanent, on-chain operation.

Registration Flow - Step by Step

Step 1 - FARMER (Mobile App, offline-capable)
  Collects: operator name, cooperative ID, government land title number,
            GPS boundary as GeoJSON polygon, soil type, crop history

Step 2 - APP (on connectivity restore)
  Hashes KYC fields: SHA-256(name + coopId + titleNumber)
  Pins farm document JSON to IPFS via Pinata -> returns CID
  Pins GeoJSON boundary separately -> returns geoCID

Step 3 - APP calls XGTFarmRegistry.registerFarm()
  Params: farmId (XGF-CC-RR-NNNNN), ipfsCID, gpsHash, signerAddresses[]
  Gas cost: ~0.002 BNB (~$0.80 at current prices)
  Contract mints ERC-721 token -> emits FarmRegistered event

Step 4 - CHAINLINK ORACLE (automated, ~5-15 min)
  Queries Sentinel-2 / Landsat-9 NDVI at farm centroid
  Returns: ndviValue (float*100 as uint16), landCoverClass (uint8)
  Contract stores keccak256(ndviValue, timestamp) on-chain
  Emits GPSVerified event -> triggers 200 XGT bonus to farmer wallet

Farm ID Naming Convention

Each Farm ID encodes its geography for human readability while remaining unique:

XGF - [CC] - [RR] - [NNNNN]
 |      |      |       |
 |      |      |       Sequence number (zero-padded, global)
 |      |      Region code (2-4 chars, ISO 3166-2 subdivision)
 |      Country code (ISO 3166-1 alpha-2)
 Excalibur Global Farm prefix

Examples:
  XGF-CM-LIT-00142  (Cameroon / Littoral / Farm 142)
  XGF-BR-PAR-00891  (Brazil / Para / Farm 891)
  XGF-LR-MGB-00023  (Liberia / Margibi / Farm 23)
  XGF-US-IND-01240  (USA / Indiana / Farm 1240)

GPS and Satellite Verification

The GeoJSON polygon submitted at registration is stored off-chain (IPFS). On-chain, only keccak256(geoJsonString) is stored - this anchors the boundary without exposing exact coordinates publicly.

The Chainlink oracle job requests a composite verification: (1) NDVI value from the most recent Sentinel-2 overpass within 10 days of registration, (2) land-cover classification confirming agricultural use, (3) area calculation confirming polygon is plausibly farm-sized (0.5 ha minimum). All three checks must pass for GPSVerified to emit. Annual re-verification is triggered automatically by the contract 365 days after the last verification.

Cooperative and Multi-Signer Structure

One cooperative wallet can own multiple Farm ID NFTs. Individual farmers in the cooperative are registered as authorized signers via addAuthorizedSigner(tokenId, signerAddress). Only an authorized signer can mint harvest batches for that farm. Signers can be added or removed by the NFT owner. All signer changes emit SignerAdded / SignerRemoved events and are permanently visible in the event log.

This structure supports large cooperatives (e.g., Cameroon palm cooperatives with 200+ member farms) while maintaining per-farmer accountability on-chain.

2. Harvest Batch Tokenization

Each harvest event produces a Harvest Batch Token (HBT) - an ERC-721 NFT minted by XGTHarvestBatch.sol. The HBT is the primary unit of traceability: it travels through the supply chain, is split by processors, and is ultimately linked to retail QR codes. Its sustainability score is computed at mint time and is immutable.

Batch ID Format and Encoding

XGB - [FARM_ID] - [CROP] - [YYYYMMDD] - [SEQ]

Example:
  XGB-XGF-CM-LIT-00142-SOY-20260310-001

Where:
  XGB         = Excalibur Global Batch prefix
  FARM_ID     = Full Farm ID (links back to FIT NFT)
  CROP        = 3-char crop code (SOY, COR, COT, PAL, COC, RIC...)
  YYYYMMDD    = Harvest date UTC
  SEQ         = Daily sequence number (resets each day per farm)

This full ID is encoded into every QR code for that batch.

On-Chain Data Fields (stored in NFT)

The following fields are stored directly in contract storage and readable on-chain without IPFS:

uint256  farmTokenId          // links to XGTFarmRegistry NFT
string   batchId              // full XGB-... identifier
bytes32  ipfsCID              // IPFS CID of full batch document
uint8    sustainabilityScore  // 0-100, computed at mint, immutable
uint32   weightKg             // harvest weight
uint8    cropCode             // enum: SOY=1, COR=2, COT=3...
uint40   harvestTimestamp     // UTC unix timestamp
address  farmerWallet         // authorized signer who minted
bool     qrActivated          // set true when retailer registers QR

Sustainability Score Algorithm

The score (0-100) is computed deterministically from submitted agronomic data at mint time. It cannot be changed post-mint. The formula is encoded in the contract:

score = 0
  + irrigationScore(irrigationMethod)    // drip=30, rain=20, flood=5
  + fertilizerScore(fertilizerType)      // organic=25, synthetic=10
  + waterScore(litersPerHa)             // <300=20, 300-600=12, >600=5
  + soilHealthScore(soilScore)          // (soilScore / 100) * 15
  + ndviBonus(ndviValue)               // ndvi>0.6=10, ndvi>0.4=5, else=0

// IPCC 2019 + USDA/EPA baseline weighting applied to each component
// Maximum possible score: 100
// XGT bonus multiplier: activated at score > 70

Batch Split Protocol

When a processor divides one batch into multiple shipments, splitBatch(parentTokenId, childWeightsKg[]) is called. The contract:

  • Validates that child weights sum to parent weight (within 2% tolerance for processing loss)
  • Burns the parent HBT
  • Mints N child HBTs, each inheriting farmTokenId, sustainabilityScore, and parentBatchId
  • Emits BatchSplit(parentTokenId, childTokenIds[]) - permanently links children to origin

Child batches carry the full provenance of their parent. Consumers scanning a child batch QR see the original farm origin, sustainability score, and the split event in the chain history.

3. Supply Chain Event Tracking

The XGTSupplyChain contract records every custody transfer and condition check as an immutable, indexed on-chain event. There is no central database - the BSC event log is the source of truth for the entire supply chain history of every batch.

Farm
mintBatch() - HBT created - farmer initiates first handoff
Processor
acceptHandoff() - records facility ID, processing type, output weight
Distributor
acceptHandoff() - records transport route hash, cold chain data
Retailer
activateQR() - final custody, QR goes live for consumer scanning

Handoff Event Schema

event HandoffAccepted(
  uint256 indexed batchTokenId,
  address indexed fromAddress,
  address indexed toAddress,
  bytes32 conditionHash,   // keccak256(temp, humidity, weight, notes)
  bytes32 locationHash,    // keccak256(facilityId, GPS centroid)
  uint8   handoffType,     // 0=FarmToProcessor, 1=ProcessorToDistrib,
                           // 2=DistribToRetailer, 3=CrossBorderExport
  uint40  timestamp
);

// Condition data is stored off-chain (IPFS) and anchored by conditionHash
// Consumers can download the full condition report and verify the hash

Anomaly Detection and Flagging

Anomaly flags are emitted when condition data at a handoff exceeds defined thresholds. The contract checks thresholds autonomously when acceptHandoff is called with out-of-range data:

Anomaly codes (auto-emitted):
  TEMP_HIGH   - temperature > threshold for crop type
  TEMP_LOW    - temperature < threshold for cold chain items
  WEIGHT_LOSS - weight drop >5% beyond processing tolerance
  DELAY       - handoff timestamp >72h after previous handoff
  CHAIN_BREAK - receiving address not registered as supply chain partner

event AnomalyFlagged(
  uint256 indexed batchTokenId,
  string  anomalyCode,
  bytes32 conditionHash,
  uint40  timestamp
);
// AnomalyFlagged is permanent. It cannot be removed, overridden,
// or hidden. It appears on every consumer verification page.

Cross-Border Export Tracking

For exports to EU/US markets, an additional handoffType=3 event records customs clearance. The exporting party calls acceptHandoff with a conditionHash anchoring to an IPFS document containing:

  • Phytosanitary certificate hash
  • Customs declaration number (hashed)
  • Port of departure + destination country codes
  • EUDR due diligence reference number (if applicable)

This creates an auditable EUDR compliance trail directly from the farm GPS coordinates to the import declaration, satisfying Article 9 of EU Regulation 2023/1115.

4. QR Code Consumer Verification System

The XGTVerification contract manages QR code registration, scan event logging, and the read interface used by the consumer-facing static web page. The system is designed to require zero crypto knowledge from end consumers.

QR Code Specification

QR Payload (URL encoded):
  https://verify.excaliburglobal.farm/batch/[BATCH_ID]?c=[CONTRACT_ADDR]

Example:
  https://verify.excaliburglobal.farm/batch/
  XGB-XGF-CM-LIT-00142-SOY-20260310-001
  ?c=0x[XGTHarvestBatch contract address]

QR Format:  QR Code version 5+ (handles 64-char URL minimum)
Error Correction: Level M (15% damage tolerance)
Module size: minimum 2mm for 300dpi print (standard food label)
NFC optional: NTAG213 chip with same URL for premium products

Consumer Verification Page - Data Sources

Page loads (static HTML/JS from IPFS):
  1. Parse BATCH_ID and CONTRACT_ADDR from URL
  2. Call XGTHarvestBatch.getBatchData(batchId) via BSC RPC
     -> farmTokenId, sustainabilityScore, weightKg, harvestDate
  3. Call XGTFarmRegistry.getFarmData(farmTokenId) via BSC RPC
     -> farmId, country, ipfsCID
  4. Fetch IPFS document at ipfsCID
     -> farm name, GPS centroid, cooperative name, NDVI image CID
  5. Call XGTSupplyChain.getFullCustodyChain(batchTokenId)
     -> full handoff history with timestamps and anomaly flags
  6. Render Google Maps embed at farm GPS centroid
  7. Display BSCScan link to token for independent verification

Total RPC calls: 3 (batched as multicall)
Page load target: <2 seconds on 3G

Consumer Display - What the User Sees

  • Farm card: Farm ID, country, region, registered date, satellite NDVI image
  • Harvest card: Crop type, harvest date, weight, sustainability score (color-coded badge)
  • Supply chain timeline: Each handoff with actor type, timestamp, condition summary, and anomaly flag if present
  • Verification badge: Green checkmark if no anomalies; yellow warning if anomaly flags exist
  • Independent verify link: Direct BSCScan URL to the on-chain token for technical users
  • No login, no wallet, no app download required - works on any browser that can scan a QR code

Counterfeit and Duplication Prevention

QR uniqueness: Each Batch ID maps to exactly one HBT token on-chain. Duplicating the QR label still points to the same blockchain record, which shows the original farm origin - making product substitution immediately visible.

Scan logging: The XGTVerification contract logs QRScanned(batchId, scannerIP_hash, timestamp) events. Abnormal scan patterns (e.g., 10,000 scans in 1 hour from the same IP range) trigger an off-chain alert to the Excalibur operations team.

Retailer lock: Once a retailer calls activateQR(batchTokenId), the QR is live. If the same QR is scanned before activation, the verification page shows "Product not yet in retail custody" - alerting to a potential supply chain leak.

Offline resilience: The React Native mobile app queues all transactions locally when the device is offline. Farmers in areas with weekly connectivity (common in rural Cameroon and Liberia) can still participate fully.
